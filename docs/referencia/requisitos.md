| RF-11 | Gestión y Resolución de Desafíos | Estudiante | Envío de la respuesta al desafío | El sistema debe permitir que el estudiante envíe una respuesta o solución al desafío que está resolviendo. | CU02 - Resolver un desafío | 3 |
| RF-12 | Gestión y Resolución de Desafíos | Sistema | Validación de la respuesta | El sistema debe validar automáticamente la respuesta enviada por el estudiante y determinar si es correcta o incorrecta. | CU02 - Resolver un desafío | 3 |
| RF-13 | Gestión y Resolución de Desafíos | Sistema | Registro de intentos | El sistema debe registrar cada intento del estudiante sobre un desafío, incluyendo el resultado obtenido, el tiempo empleado y el número de intento. | CU02 - Resolver un desafío | 3 |

| RF-15 | Asistencia Dinámica (Generación de Pistas) | Sistema (LLM) | Generación de pista mediante el LLM | El sistema debe generar, mediante el modelo LLM integrado, una pista acorde al nivel de ayuda vigente del estudiante (pista general, ejemplo guiado, solución parcial o solución completa). | CU03 - Solicitar ayuda adaptativa (pista dinámica) | 3 |

| RF-17 | Asistencia Dinámica (Generación de Pistas) | Sistema | Registro de solicitudes de ayuda | El sistema debe registrar cada solicitud de ayuda realizada, incluyendo el nivel de ayuda entregado y el momento en que se solicitó. | CU03 - Solicitar ayuda adaptativa (pista dinámica) | 2 |

| RF-21 | Retiro Dinámico de Asistencia | Estudiante | Notificación del cambio de nivel de asistencia | El sistema debe notificar al estudiante cuando su nivel de asistencia disponible cambie como resultado de la evaluación de su desempeño. | CU04 - Ajustar el nivel de asistencia según desempeño | 2 |

| RF-23 | Seguimiento y Visualización de Progreso | Estudiante | Indicadores históricos de desempeño | El sistema debe mostrar de forma gráfica la evolución histórica de los indicadores de desempeño del estudiante a lo largo del uso de la plataforma. | CU05 - Consultar seguimiento y progreso | 2 |
| RF-24 | Seguimiento y Visualización de Progreso | Estudiante | Filtrado del historial de intentos | El sistema debe permitir filtrar el historial de intentos del estudiante por desafío y por rango de fechas. | CU05 - Consultar seguimiento y progreso | 1 |

## Requisitos no funcionales (RNF-nn = Nro.)

| ID | FURSP+ | Nombre | Descripción |
|---|---|---|---|
| RNF-01 | P - Performance | Tiempo de respuesta de la API | Las peticiones REST del backend (FastAPI) que no involucren al LLM deben responder dentro de un tiempo máximo aceptable bajo condiciones normales de operación. |
| RNF-02 | P - Performance | Latencia de generación de pistas | La generación de una pista mediante el LLM debe completarse dentro de un tiempo que no interrumpa el flujo de resolución del estudiante. |
| RNF-03 | P - Performance | Tiempo de actualización del estado de sesión | La actualización del nivel de asistencia vigente en Redis, tras evaluar el desempeño del estudiante, debe reflejarse de forma casi inmediata en la sesión activa. |
| RNF-04 | P - Performance | Capacidad de usuarios concurrentes | El sistema debe soportar el uso simultáneo de un número mínimo de estudiantes sin degradar el tiempo de respuesta definido en RNF-01. |
| RNF-05 | F - Functionality (Seguridad) | Autenticación basada en JWT | El acceso a los recursos protegidos de la API debe requerir un token JWT válido, con expiración configurada. |
| RNF-06 | F - Functionality (Seguridad) | Almacenamiento seguro de contraseñas | Las contraseñas de los usuarios deben almacenarse utilizando un algoritmo de hash seguro con sal (salt), nunca en texto plano. |
| RNF-07 | F - Functionality (Seguridad) | Comunicación cifrada | Toda comunicación entre el frontend, el backend y los servicios externos (incluido el proveedor del LLM) debe realizarse mediante conexiones cifradas. |
| RNF-08 | F - Functionality (Seguridad) | Control de acceso por rol | El sistema debe restringir el acceso a las funciones administrativas (gestión del banco de desafíos, reportes) únicamente a usuarios con rol de administrador o docente. |
| RNF-09 | R - Reliability | Disponibilidad del sistema | La plataforma debe estar disponible para su uso durante el periodo de validación con estudiantes, minimizando las interrupciones no planificadas. |
| RNF-10 | R - Reliability | Persistencia del estado de sesión | El estado de sesión gestionado en Redis (nivel de asistencia, umbrales, temporización) no debe perderse ante una recarga de página o una breve interrupción de red. |
| RNF-11 | R - Reliability | Tolerancia a fallos del proveedor del LLM | Ante la falta de disponibilidad o error del servicio del LLM, el sistema debe informar al estudiante de forma controlada, sin afectar el resto de las funciones de la plataforma. |
| RNF-12 | R - Reliability | Respaldo de la base de datos | La información almacenada en PostgreSQL (usuarios, intentos, ayudas, resultados) debe respaldarse periódicamente para permitir su recuperación. |
| RNF-13 | U - Usability | Facilidad de aprendizaje de la interfaz | Un estudiante debe ser capaz de completar el flujo de autenticación y de resolución de un primer desafío sin requerir instrucción adicional. |
| RNF-14 | U - Usability | Diseño responsivo | La interfaz debe adaptarse correctamente a distintos tamaños de pantalla, priorizando el uso desde computadoras de escritorio y laptops en el contexto del curso. |
| RNF-15 | U - Usability | Retroalimentación visible al estudiante | El sistema debe comunicar de forma clara al estudiante el resultado de sus acciones (envío de respuesta, solicitud de ayuda, cambio de nivel de asistencia). |
| RNF-16 | S - Supportability | Escalabilidad horizontal del backend | La arquitectura del backend (FastAPI) debe permitir el despliegue de instancias adicionales ante un incremento en la carga de usuarios. |
| RNF-17 | S - Supportability | Documentación de la API | La API REST del backend debe estar documentada de forma automática y accesible, facilitando su mantenimiento y la integración con el frontend. |
| RNF-18 | S - Supportability | Arquitectura modular | El sistema debe organizarse en módulos independientes (autenticación, generador de desafíos, motor de retiro de asistencia, capa analítica) que puedan modificarse o probarse por separado. |
| RNF-19 | Restricción de implementación | Trazabilidad del código y control de versiones | Todo el código fuente del proyecto debe mantenerse bajo un sistema de control de versiones, con historial de cambios trazable. |
| RNF-20 | S - Supportability | Compatibilidad con navegadores | El frontend debe funcionar correctamente en los navegadores web de mayor uso entre los estudiantes del contexto de aplicación. |
| RNF-21 | S - Supportability | Independencia del proveedor del LLM | La integración con el modelo de lenguaje debe diseñarse de forma que permita sustituir o actualizar el proveedor del LLM sin rediseñar el resto del sistema. |
| RNF-22 | Restricción legal/ética | Consentimiento informado de los participantes | Los estudiantes que participen en la validación (cuestionario de línea base y registro de intentos) deben ser informados sobre el uso de sus datos con fines de la tesis. |
| RNF-23 | F - Functionality (Privacidad) | Anonimización de datos para el análisis | Los datos utilizados en el análisis de resultados (capa analítica) deben tratarse de forma anonimizada o seudonimizada, evitando la exposición de información personal identificable. |
| RNF-24 | F - Functionality (Privacidad) | Minimización de datos enviados al LLM | El contenido enviado al proveedor del LLM para la generación de pistas debe limitarse a la información estrictamente necesaria (enunciado del desafío, nivel de ayuda, código, el resultado obtenido y el mensaje del estudiante.), evitando el envío de datos personales del estudiante. |
